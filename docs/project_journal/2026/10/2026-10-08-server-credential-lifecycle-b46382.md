# Server-Owned Credential Lifecycle

## Approved Boundary
- Continue the third slice of [Playback Reliability Follow-Ups](2026-10-05-playback-reliability-followups-b46380.md), from merged PR #73 and `master` commit `d8a13b4aa76daefec5d00542ec3912f0710d4582`.
- Integrate the independent review-request-token rollout from `master` commit `2482b6fba9dddcf11f3ede03ccdd880273da63af` before final consumer validation. It changes the gate controller and a separate journal only; the credential implementation remains intact.
- The LAN server owns login ticket creation, provider polling/callback validation, account verification, automatic renewal, and private credential storage. Remote macOS/tvOS clients only initiate login, display a QR code or server-issued link, and query redacted state.
- No remote credential-management pairing, client-submitted cookie/key RPC, account-switching API, physical Apple TV validation, or TLS rollout is introduced.
- Reuse healthy saved credentials and refresh material. Preserve unrelated profiles, credential kinds, and the global default; do not ask for login merely because a credential already exists.

## Implementation Sequence
1. Add a narrow, typed BBDown core account-identity probe using the existing official Web/OAuth endpoints and signing implementation. The current pinned API exposes validity but not the identity required for cross-kind and existing-profile checks. Keep the dirty BBDown source checkout untouched by using an isolated worktree and separate prerequisite PR.
2. Update the exact BBDown revision after the prerequisite lands. Its current mainline is core `0.7.0`; run the complete server regression suite rather than assuming the dependency change is metadata-only.
3. Add server-owned credential readiness, bounded automatic Web-cookie maintenance, and same-account Web QR reauthorization. Persist verified account bindings privately so an expired credential does not silently authorize switching an existing profile to another account.
4. Add a server-hosted generic access-key browser handoff. The advertised media origin owns its page and completion endpoint; a short-lived, one-use session capability is carried in the login-link fragment. Browser messages must match the issued provider origin and window, and completion must verify the key's account against the profile before storing it.
5. Extend the shared client models and macOS/tvOS login presentation with additive login-method and redacted-readiness fields. Clients never process OAuth credential messages or return credential material through gRPC.
6. Reload configured server-default credentials for new playback requests after renewal without restarting the adapter. Persisted anonymous request contexts remain anonymous; explicit profile selection continues to use that profile.

## Protected Properties
- **Account identity:** successful official provider probes establish positive account IDs. Renewal and replacement must retain the already verified account; malformed, unverifiable, or mismatched identities fail closed.
- **Credential content:** private compare-and-replace checks bind each write to its observed credential/refresh material. Unrelated credential kinds and profiles are preserved; a stale callback cannot overwrite a newer credential.
- **Post-login readiness:** after publishing Web login success and releasing its reservation, the existing login task immediately verifies a preserved generic key without waiting for periodic maintenance. The bounded probe publishes only if its operation, complete credential bundle, and private Web binding still match; stale cleanup cannot remove a newer readiness record. Valid, rejected, and temporarily unverifiable keys remain distinct outcomes. This follow-up does not write credentials or delay the completed QR session's response.
- **Binding content:** a persistent exclusive file lock serializes the complete read/check/update/publication transaction across cooperating processes, including writes to different profiles. Expected-entry comparisons still reject stale same-profile updates. Lock contention is bounded to two seconds; non-regular, symlinked, or unsafe Unix lock/data files report unavailable storage. This does not protect against a malicious same-UID writer that bypasses or replaces the lock, and does not compare benign timestamp or directory-entry changes.
- **Login authority:** profile reservation, expiry, one-use completion, server-configured origin, and an unguessable session capability constrain the browser callback. An `Origin` header alone is not authentication.
- **Client login availability:** readiness is evaluated separately for Web cookies and generic keys. A clean profile completes Web login before obtaining a generic key; a ready key does not block obtaining a missing Web cookie. Modern clients require ready Web credentials before offering generic-key login. Login start has an independent default timeout of at least 90 seconds in both the view model and transport, preserving longer configured timeouts without extending normal status/poll calls. A pending or starting session, unsupported capability, unavailable readiness, or invalid/stale endpoint still prevents starting a login.
- **Browser handoff bounds:** same-origin server links accept percent-encoded spaces and Unicode in an advertised prefix, while rejecting path separators, traversal, controls, and dangerous nested encodings. Server capability advertisement applies the same bounded path rules as clients; generic media URI normalization is unchanged. Each candidate/base URI remains bounded to 4 KiB. HTTP completion allows bounded JSON escaping/envelope overhead; the decoded provider message remains limited to 16 KiB.
- **Storage access:** credentials and account bindings remain server-private. Client errors and logs expose fixed classifications only, not cookie/key values, account IDs, private paths, raw OAuth messages, or signed upstream URLs. Metadata timestamps and directory-entry churn are not evidence of credential-content mutation.
- **Publication boundary:** credential-store replacement and private account-binding replacement are separate file transactions, in that order. If binding publication fails after the credential commit, report unavailable readiness and deny generic-key login until official identity verification repairs the binding. This is not an atomic two-file transaction, and no rollback may overwrite a concurrent credential update.
- **Callback ownership:** cancellation during account verification must release completion ownership without writing credentials. Once a bounded persistence operation has claimed ownership, it must finish or fail and release the profile reservation even if the HTTP request disappears. Revalidate the session deadline and observed credential content before that claim; cancelling an async waiter does not cancel an already-running blocking write.
- **Publication freshness:** an in-flight extent must not publish against a superseded target-origin validator. When that validator is the only rebase conflict and both target-origin bindings remain present, discard the old response and permit one fresh download and admission attempt, including strong-validator appearance or disappearance. Resource/representation/data-object identity, total length, prefix, existing extent hashes, and the final publication guard remain mandatory. A missing target binding, second conflict, or content mismatch still fails closed; sampled equivalence is not a whole-object cryptographic proof.
